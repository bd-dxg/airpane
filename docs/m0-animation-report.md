# M0 动画路线报告

对应 PRD 的 T0.6：验证「DWM 缩略图 + 覆盖层」这条动画路线是否可行，并给出选型建议。

- 日期：2026-11-18
- 环境：Windows 11 build 26200、单屏 2560×1440 @100%（96 DPI）、Intel Iris Xe 核显、Rust 1.100 stable
- 原型：`prototypes/anim`（一次性的验证代码，M1 不继承）
- 运行方式：`cargo run -p airpane-anim-prototype -- 300 [--no-flush]`

## 1. 结论

**「DWM 缩略图 + 覆盖层窗口」路线可行，且 CPU 侧余量极大。**

- 覆盖层里用 `DwmRegisterThumbnail` 承载源窗口的实时画面，每帧通过 `SetWindowPos` 改变覆盖层窗口的位置与尺寸，同时用 `DwmUpdateThumbnailProperties` 把缩略图重绘到新的客户区矩形。
- 打开 `DwmFlush` 时稳定 60 FPS（16.6ms/帧），这是屏幕刷新率的上限，不是性能上限。
- 关闭 `DwmFlush` 后每帧仅 0.23ms（等效 4400 FPS），说明 CPU 与 DWM 提交都不是瓶颈。
- 代价只有一个：**动画期间源窗口本身不动，用户看到的是它的缩略图在动**，落位时真实窗口一次性跳过去，需要靠「先落位、后撤覆盖层」的顺序掩盖切换瞬间。

## 2. 实测数据

每组为一次往返动画（舞台 → 缩略图 → 舞台，各 300ms）。

| 配置 | 帧数 | 平均帧耗时 | p95 | 最大 | 等效 FPS | 进程 CPU |
| --- | --- | --- | --- | --- | --- | --- |
| `DwmFlush`（默认） | 39 | 16.59ms | 18.35ms | 18.71ms | 60.3 | 9.7% |
| `DwmFlush`（复测） | 39 | 16.33ms | 18.79ms | 18.88ms | 61.2 | 7.4% |
| 关闭同步（吞吐） | 2669 | 0.23ms | 0.95ms | 4.87ms | 4443.9 | 78.0% |
| 关闭同步（复测） | 2547 | 0.24ms | 1.02ms | 6.26ms | 4241.0 | 52.0% |

解读：

- 60 FPS 那两组的帧耗时几乎等于 1/60 秒，说明每帧都在等垂直同步；CPU 占用 7%–10% 里大部分是 `DwmFlush` 的自旋等待。
- 关同步那组的 CPU 占用高是「无节流全速跑」的结果，不代表真实动画的开销。真实动画会被垂直同步限制在 60 帧/秒，CPU 开销约等于 `0.23ms × 60 ≈ 14ms/s`，即 1.4%。
- 核显的 GPU 负担来自 DWM 合成缩略图本身，本次没有可用的 GPU 计数器（任务管理器手读不稳定），只记录定性观察：动画期间没有可见掉帧。

## 3. 关键技术发现

### 3.1 DWM 缩略图只认目标窗口矩形

`DwmRegisterThumbnail`/`DwmUpdateThumbnailProperties` 把源窗口画面绘制到**目标窗口客户区的指定矩形**里，由 DWM 在合成阶段贴上。它不是目标窗口内部的图层，因此：

- 目标窗口内的任何绘制（GDI、Direct2D、DirectComposition 视觉树变换）都**不会**影响缩略图。
- 想让缩略图缩放或位移，只能改变目标窗口的位置/尺寸，或者改变 `rcDestination` 矩形。
- 本次原型同时用了这两种手段：窗口矩形随动画变化，`rcDestination` 同步设为整个客户区。

这也意味着 PRD 5.4 里「在 DirectComposition 视觉树上对缩略图做变换」的设想不成立：缩略图不参与视觉树。**原型没有单独实现 DComp 视觉树版本**，因为从机制上就可以判定它不会影响缩略图；如果后续要在缩略图之外再叠一层自绘内容（标题、圆角遮罩），DComp 仍然是用得上的，但那是叠加层，不是缩略图本身。

### 3.2 覆盖层窗口的样式约束

原型使用 `WS_EX_NOACTIVATE | WS_EX_TOOLWINDOW | WS_EX_TOPMOST` 的 `WS_POPUP` 窗口，与预览区一致。实测：

- 动画期间不会抢焦点，用户正在输入的窗口不受影响。
- `SWP_NOZORDER` 保持置顶，不会因为每帧 `SetWindowPos` 引起 z-order 抖动。
- 每帧调用 `InvalidateRect` 是空操作（背景纯色），但保留它是为了让窗口在尺寸变化时正确擦除旧区域；如果去掉，缩小动画会留下残影。

## 4. 与 Windows.Graphics.Capture 的对比（定性）

PRD 5.4 的备选路线是 `Windows.Graphics.Capture` 抓帧到 D3D11 纹理再自绘。基于本次原型的数据，暂时**不建议**切换：

| 维度 | DWM 缩略图 + 覆盖层 | Windows.Graphics.Capture |
| --- | --- | --- |
| 帧开销 | 0.23ms/帧（实测，含 DWM 提交） | 需要自建 D3D11 设备、纹理与合成，预计 1–3ms/帧 |
| 动画自由度 | 只能缩放/移动整个窗口矩形 | 可对画面任意变换、加遮罩与圆角 |
| 版本与边框 | 无额外要求 | 需要处理 Win10 捕获边框、版本下限 |
| 与现有代码的关系 | 预览区已经在用 DWM 缩略图，零额外基础设施 | 需要一套独立的抓帧与渲染栈 |

结论：v1 继续走 DWM 缩略图 + 覆盖层。只有出现下面两种情况之一时才重新评估抓帧路线：

1. 需要在动画中做非矩形变换（例如弧形路径、圆角裁剪、模糊）。
2. 覆盖层窗口的每帧 `SetWindowPos` 在某些应用上引起可见撕裂（需要 M3 的兼容性测试确认）。

## 5. 对 PRD 的修正建议

- PRD 5.4 的「覆盖层上对缩略图做缩放、位移」应改写为「覆盖层窗口自身按动画进度缩放/位移，缩略图目标矩形同步更新」。
- PRD 5.4 的「使用 `DwmFlush` 或垂直同步对齐帧」得到实测支持：开 `DwmFlush` 是必要的，否则会来不及等待真实窗口落位。
- 落位时序建议确定为：动画到最后一帧 → `SetWindowPos` 移动真实窗口 → 保留覆盖层 1–2 帧 → 隐藏覆盖层。M3 需要按这个顺序实现并验证闪烁。
