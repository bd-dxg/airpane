# 决策记录

本文件记录 PRD 未覆盖、或与 PRD 原文不一致的决策，是这些点的唯一真相源。PRD（`docs/PRD.md`）自 2026-11-18 起冻结为草案基线，不再随实施修订。

格式：每条包含编号、日期、决策、理由、影响范围。新增决策追加到末尾，不修改历史条目；决策被推翻时新增一条并在旧条目上标注「已由 D-xxx 取代」。

## D-001 开发期默认非提权运行

- **日期**：2026-11-18
- **决策**：开发与调试阶段以普通权限运行，`cargo run` 不触发 UAC；只有发行版通过任务计划程序以最高权限自启（PRD 4.6 / 5.8）。
- **理由**：每次调试都过 UAC 会打断事件监听与窗口操作的调试节奏。开发期把提权窗口标记为「不可管理」即可暴露降级路径，UIPI 相关问题在 T0.x 的提权终端专项复测里覆盖。
- **影响**：M0–M2 的开发流程；发布配置（自启任务、以最高权限运行）在 M3 接入。

## D-002 M0 只验证 DWM + 覆盖层动画路线

- **日期**：2026-11-18
- **决策**：不按 PRD T0.6 同时做两条原型。先只验证「DWM 缩略图 + DirectComposition 覆盖层」，只有该路线被证伪时才补 Windows.Graphics.Capture 原型。
- **理由**：DWM 缩略图是 PRD 5.4 的首选路线且开销最低；两条路线各做一遍会让 M0 工作量翻倍，而 WGC 在 Win10 上的捕获边框与版本下限问题本机无法验证。
- **影响**：`docs/m0-animation-report.md` 的结论形态；若走 WGC，报告必须写明证伪依据与代价。

## D-003 M0 只在 Windows 11 上验收

- **日期**：2026-11-18
- **决策**：PRD 中「M0 在 Win10 22H2 与 Win11 上都跑通」改为「M0 在 Windows 11（build 26200）上跑通」，Win10 22H2 兼容性整体推到 M4。
- **理由**：开发机只装了 Windows 11 build 26200，没有 Win10 实机或虚机。
- **影响**：Win10 专属风险（无 Mica、DWM 行为差异）在 `docs/test-report-M0.md` 里作为已知缺口列出，不阻塞 M0 验收。

## D-004 M0 不改动任何真实窗口的位置与尺寸

- **日期**：2026-11-18
- **决策**：M0 只验证「枚举 + 事件 + 预览区缩略图 + 点击前置」，不调用会改变其他窗口位置或尺寸的接口。窗口落位、居中与尺寸记忆留到 M1。
- **理由**：`SetWindowPos` 改尺寸是最容易引发应用重排与闪烁的环节，在窗口状态持久化与还原机制就位之前触碰它，会让窗口有停在异常位置的风险。
- **影响**：M0 不验收 Stage 布局；M1 的 T1.2 才引入布局。

## D-005 一开始就建立窗口快照层

- **日期**：2026-11-18
- **决策**：从 T0.1 起就建立「窗口快照 + 唯一允许调 `SetWindowPos` 的封装」这一层：快照生成 M0 就实现并在每次操作前写入磁盘，恢复路径留到 M1 的 T1.1。M0 因为不改窗口，该封装不会被实际调用。
- **理由**：PRD 11.3 第 3 条要求任何移动/缩放前必须落盘，若 M0 豁免，M1 要回头改所有调用点。

## D-020 事件同步采用「事件驱动 + 1Hz 校准」的混合模型

- **日期**：2026-11-18
- **决策**：`SetWinEventHook`（`WINEVENT_OUTOFCONTEXT`）负责秒内响应，另以 1 次/秒的频率对已跟踪窗口重新分类并校准列表。不再假设纯事件流能维持一致。
- **理由**：T0.3 实测（Win11 build 26200，12 轮强杀记事本）发现 `EVENT_OBJECT_DESTROY` **完全没有投递**，12 次进程退出收到 0 个 destroy 事件；同时 `WS_EX_*` 与 owner 的变化不产生任何 WinEvent。只靠事件会让已退出的窗口永久留在预览区。
- **影响**：PRD 5.3 的「避免轮询」改为「避免高频轮询」，1Hz 校准保留（PRD 5.7 允许每秒一次校验）；M1 的窗口模型必须包含同样的校准步骤。

## D-021 窗口分类要求顶层窗口且无 owner

- **日期**：2026-11-18
- **决策**：除不可见、DWM cloak、`WS_EX_TOOLWINDOW`、系统壳窗口外，窗口还必须是顶层窗口（`GetAncestor(hwnd, GA_ROOT) == hwnd`），且无 owner（有 owner 时只有带 `WS_EX_APPWINDOW` 才保留）。
- **理由**：记事本（Win11 版本）会创建大量名为 `Non Client Input Sink Window`、空标题的子窗口与附属窗口，并在创建时临时可见。缺少这两条规则时，一次 12 轮开关测试会在预览区模型里堆积 70+ 个幽灵窗口。
- **影响**：`airpane-core::window` 的 `WindowFacts` 增加 `top_level`、`owned`、`app_window`；新增 `RejectReason::NotTopLevel` 与 `RejectReason::OwnedPopup`。

## D-027 日志自写，不引入 tracing

- **日期**：2026-11-19
- **决策**：M1 的日志由 `airpane-platform-win::logging` 自实现：级别过滤、单文件 1MB、保留 `airpane.1.log` 到 `airpane.3.log` 三份历史、本地时间戳。不引入 `tracing` + `tracing-subscriber` + `tracing-appender`。
- **理由**：PRD 5.1 只是「建议」`tracing`。M1 需要的只有「把崩溃前最后几步留下来」，自写模块约 150 行、零新依赖、不改 CI 编译时间；`tracing` 的结构化字段与过滤能力在 M1 没有使用场景。M4 做日志导出时若确实需要结构化查询，再评估替换。
- **影响**：`docs/DEPENDENCIES.md` 不变；日志只写 hwnd、pid、进程名、错误码与状态迁移，不写窗口标题、窗口内容与用户输入（PRD 11.3 第 5 条）。

## D-029 状态文件按生命周期分三份

- **日期**：2026-11-19
- **决策**：`%APPDATA%\AirPane\` 下分四个文件：用户设置 `config.json`、崩溃恢复 `snapshot.json`、尺寸记忆 `window-sizes.json`、日志 `logs\airpane.log`。`APPDATA` 缺失时回退到可执行文件同级目录，保证便携运行也能留下文件。
- **理由**：三类数据生命周期不同——配置由用户手改，快照每次进入 Stage 都要重写，尺寸记忆由程序自动学习。混在一个文件里会让「每次移动窗口都重写用户配置」这种荒谬的写入模式出现，也让损坏时无法只重置其中一类。快照损坏时不该丢掉用户设置，反之亦然。
- **影响**：`airpane-platform-win::paths` 是唯一拼路径的地方；写快照不得触碰 `config.json`。

## D-024 退出还原与崩溃恢复的语义

- **日期**：2026-11-19
- **决策**：正常退出（快捷键退出、`WM_CLOSE`、进程结束前）先把所有被本程序移动过的窗口还原到快照位置，再把快照标记为 `clean_exit = true`；启动时读到 `clean_exit == false` 的快照，按快照恢复窗口位置后清除快照。只有快照里 `ShowState::Normal` 的窗口参与恢复：最大化与最小化窗口不会被 Stage 搬动（D-026），没有位置可还原。
- **理由**：AirPane 不在运行时，桌面上不应该存在形变过的窗口。同时，「未清理的快照」是崩溃与强杀的唯一信号，比在别处维护一个「上次是否正常退出」的独立标记更不容易失效。
- **影响**：`core::snapshot` 的 `SnapshotFile` 增加 `clean_exit`，版本升到 2；`platform-win::snapshot_store` 负责读写的原子性；`app::recovery` 是唯一的恢复入口。

## D-030 位置与尺寸统一使用 DWM 可见边界

- **日期**：2026-11-19
- **决策**：项目内所有窗口位置与尺寸计算（枚举结果、快照、舞台区居中、移动目标）统一使用 `DwmGetWindowAttribute(DWMWA_EXTENDED_FRAME_BOUNDS)`，拿不到时才回退 `GetWindowRect`。`SetWindowPos` 接受的是含阴影的外框，由 `platform-win::placement::move_window` 内部做一次补偿。
- **理由**：手工验证时发现，把 `GetWindowRect` 的结果当作「可见边界」再交给 `move_window` 补偿，会导致窗口每移动一次就膨胀一圈 —— 微信窗口从 1053×992 变成 1147×1079，因为 Qt 窗口的阴影外扩接近 50px。两处使用不同坐标系是这类 bug 的唯一来源，所以只允许一种语义。
- **影响**：`platform-win::window::extended_frame_bounds` 成为唯一的边界读取入口；`WindowInfo::rect` 与快照里的 `rect` 语义随之变为可见边界；`move_window` 的入参必须是同一语义的矩形。
## D-022 只移动当前活跃窗口，其余窗口原地不动

- **日期**：2026-11-19
- **决策**：Stage 模式下每次切换只对当前活跃窗口调一次 `SetWindowPos`，其余窗口保持原位。它们的缩略图在预览区里展示，点击即切换。
- **理由**：每轮切换只动一个窗口，闪烁与崩溃风险最小；被移动过的窗口集合最多等于用户实际用过的窗口数，快照与还原逻辑简单。代价是观感与 macOS 台前调度不同（其余真窗口不会堆到左侧），但预览区已经提供了同样信息的空间入口。
- **影响**：`app::App` 的 `moved` 集合；退出时按它逐个还原（D-024）。

## D-023 活跃窗口 = 前台窗口，实时跟随

- **日期**：2026-11-19
- **决策**：不区分「点缩略图切换」与「Alt+Tab / 任务栏 / 新开窗口」，只要可管理窗口成为前台就搬进舞台区。
- **理由**：唯一真相源是前台窗口，不需要额外的状态机，也不会出现「前台是 A、舞台区里是 B」的不一致。用户的反馈是 3 天自用后再判断要不要改成「仅点缩略图才移动」，M1 先按跟随实现。
- **影响**：`App::focus_window` 只由 `EVENT_SYSTEM_FOREGROUND` 驱动；M2 的暂停机制要在这一层前面加过滤。

## D-025 尺寸记忆按句柄优先、进程 + 类名回退，只记尺寸不记位置

- **日期**：2026-11-19
- **决策**：会话内按 hwnd 记录，跨运行按 `(process_name, class_name)` 合并；下次窗口进入舞台区时用记住的尺寸居中放置。占满舞台区的尺寸不记录。
- **理由**：同一应用的多个窗口在会话内必须分开，重启后能继承大致尺寸即可。位置每次由舞台区几何重算，预览区宽度或分辨率变化时窗口不会偏出舞台区。记录满屏尺寸没有记忆价值，只会让窗口永远满屏。
- **影响**：`core::window_sizes::WindowSizeStore`；`window-sizes.json`（D-029）。

## D-026 M1 的最小全屏/最大化保护

- **日期**：2026-11-19
- **决策**：前台窗口处于最大化，或可见边界覆盖整个主显示器（允许 1px 误差）时，不移动、不缩放它，只在日志记一条；仍把它记为活跃窗口，避免预览区把它列成可切换项。
- **理由**：3 天自用必然遇到全屏视频与游戏。完整规则（进程名单、`SHQueryUserNotificationState`、暂停与 1 秒防抖）留给 M2，M1 只做「别去动它」这一条。
- **影响**：`platform-win::monitor::should_skip_placement`；`App::focus_window` 的跳过分支。

## D-031 系统 UI 宿主进程不进入预览区

- **日期**：2026-11-19
- **决策**：`StartMenuExperienceHost.exe`、`SearchHost.exe`、`ShellExperienceHost.exe`、`TextInputHost.exe`、`LockApp.exe` 的窗口一律排除，新增 `RejectReason::ShellProcess`。`WindowFacts` 增加 `process_name`。
- **理由**：手工验收时启动瞬间的前台窗口是开始菜单宿主，它通过了原有的可见性、顶层、类名规则，被当成普通窗口搬进了舞台区。这类窗口由系统 UI 进程创建，搬走会直接破坏开始菜单、搜索、音量面板与输入法候选框。类名规则拦不住它们（Win11 开始菜单用的是通用 XAML 宿主类名）。
- **影响**：`core::window::classify` 增加进程名判定；后续 M2 的用户自定义排除名单走同一条路径。

## D-032 预览区宽度从配置读取并应用 D-012 钳制

- **日期**：2026-11-19
- **决策**：`Strip::create` 接收配置里的 `strip.width_dip`，实际宽度 = `effective_strip_width` 的结果按窗口 DPI 换算成物理像素。
- **理由**：M0 把 200 DIP 写死在 `strip` 里，配置项形同虚设。现在宽度只有一条计算路径，舞台区宽度也直接用预览区的实际宽度，两者不会对不上。
- **影响**：`Strip::width()` 是舞台区计算的唯一输入；改宽度只需改配置文件。
## D-028 首次启动默认进入 Stage 模式

- **日期**：2026-11-19
- **决策**：配置项 `startup.mode` 的取值 `last`（默认）在 M1 等同于 `stage`；`normal` 会让程序以普通桌面模式启动。真正的「上次状态」需要单独记录运行态，留到 M3 设置面板。
- **理由**：M1 还没有设置面板与引导，默认形态是用户发现程序在工作的唯一方式。把「上次状态」塞进 `config.json` 会让程序每次切换模式都重写用户配置文件，违反 D-029 的生命周期划分。
- **影响**：`app::main` 的启动分支；M3 决定是否引入独立的运行态文件。

## D-033 工具区文字 M1 硬编码，M3 换资源表

- **日期**：2026-11-19
- **决策**：预览区底部工具区的两个按钮文字（「设置」「桌面」）在 M1 以常量数组写死在 `airpane-strip`，集中在一个 `TOOLBAR_LABELS` 里。
- **理由**：PRD 11.3 第 8 条要求用户可见文字走多语言资源，但 M1 没有任何资源系统，为一个 40 像素高的工具栏引入 i18n 框架不划算。集中成常量是为了 M3 引入资源表时只需要改一处。
- **影响**：`crates/strip/src/window.rs` 的 `TOOLBAR_LABELS`；M3 设置面板落地时必须一起处理这条硬约束。

## D-034 最小化窗口：先同步还原再搬入，尺寸只记普通状态

- **日期**：2026-11-19
- **决策**：前台窗口处于最小化时，`App::focus_window` 先调用 `foreground::restore`（同步 `ShowWindow(SW_RESTORE)`），重新读取矩形后再走正常搬入流程。尺寸记忆只记录 `ShowState::Normal` 的窗口，且尺寸不小于舞台区时不记。
- **理由**：`SetWindowPos` 对最小化窗口只修改「还原位置」，窗口仍留在 `-32000` 一行，表现为「日志说已移入舞台区，窗口却还在任务栏」。而 `activate` 里的 `ShowWindowAsync` 是异步的，紧接着读到的矩形可能还是最小化时的 `146x21`，这个尺寸一旦写进尺寸记忆，下次进入舞台区就会按它居中，窗口变成一条细缝。
- **影响**：`platform-win::foreground::restore` 是唯一同步还原入口；`App::remember_size` 增加状态与尺寸下限两个前置条件。
