# 决策记录

本文件记录 PRD 未覆盖、或与 PRD 原文不一致的决策，是这些点的唯一真相源。PRD（`docs/PRD.md`）自 2026-11-18 起冻结为草案基线，不再随实施修订。

格式：每条包含编号、日期、决策、理由、影响范围。新增决策追加到末尾，不修改历史条目；决策被推翻时新增一条并在旧条目上标注「已由 D-xxx 取代」。

## D-001 开发期默认非提权运行

- **日期**：2026-11-18
- **决策**：开发与调试阶段以普通权限运行，`cargo run` 不触发 UAC；只有发行版通过任务计划程序以最高权限自启（PRD 4.6 / 5.8）。
- **理由**：每次调试都过 UAC 会打断事件监听与窗口操作的调试节奏。开发期把提权窗口标记为「不可管理」即可暴露降级路径，UIPI 相关问题在 T0.x 的提权终端专项复测里覆盖。
- **影响**：M0–M2 的开发流程；发布配置（自启任务、以最高权限运行）在 M3 接入。

## D-002 M0 只验证 DWM + 覆盖层动画路线

- **日期**：2026-11-18
- **决策**：不按 PRD T0.6 同时做两条原型。先只验证「DWM 缩略图 + DirectComposition 覆盖层」，只有该路线被证伪时才补 Windows.Graphics.Capture 原型。
- **理由**：DWM 缩略图是 PRD 5.4 的首选路线且开销最低；两条路线各做一遍会让 M0 工作量翻倍，而 WGC 在 Win10 上的捕获边框与版本下限问题本机无法验证。
- **影响**：`docs/m0-animation-report.md` 的结论形态；若走 WGC，报告必须写明证伪依据与代价。

## D-003 M0 只在 Windows 11 上验收

- **日期**：2026-11-18
- **决策**：PRD 中「M0 在 Win10 22H2 与 Win11 上都跑通」改为「M0 在 Windows 11（build 26200）上跑通」，Win10 22H2 兼容性整体推到 M4。
- **理由**：开发机只装了 Windows 11 build 26200，没有 Win10 实机或虚机。
- **影响**：Win10 专属风险（无 Mica、DWM 行为差异）在 `docs/test-report-M0.md` 里作为已知缺口列出，不阻塞 M0 验收。

## D-004 M0 不改动任何真实窗口的位置与尺寸

- **日期**：2026-11-18
- **决策**：M0 只验证「枚举 + 事件 + 预览区缩略图 + 点击前置」，不调用会改变其他窗口位置或尺寸的接口。窗口落位、居中与尺寸记忆留到 M1。
- **理由**：`SetWindowPos` 改尺寸是最容易引发应用重排与闪烁的环节，在窗口状态持久化与还原机制就位之前触碰它，会让窗口有停在异常位置的风险。
- **影响**：M0 不验收 Stage 布局；M1 的 T1.2 才引入布局。

## D-005 一开始就建立窗口快照层

- **日期**：2026-11-18
- **决策**：从 T0.1 起就建立「窗口快照 + 唯一允许调 `SetWindowPos` 的封装」这一层：快照生成 M0 就实现并在每次操作前写入磁盘，恢复路径留到 M1 的 T1.1。M0 因为不改窗口，该封装不会被实际调用。
- **理由**：PRD 11.3 第 3 条要求任何移动/缩放前必须落盘，若 M0 豁免，M1 要回头改所有调用点。

## D-020 事件同步采用「事件驱动 + 1Hz 校准」的混合模型

- **日期**：2026-11-18
- **决策**：`SetWinEventHook`（`WINEVENT_OUTOFCONTEXT`）负责秒内响应，另以 1 次/秒的频率对已跟踪窗口重新分类并校准列表。不再假设纯事件流能维持一致。
- **理由**：T0.3 实测（Win11 build 26200，12 轮强杀记事本）发现 `EVENT_OBJECT_DESTROY` **完全没有投递**，12 次进程退出收到 0 个 destroy 事件；同时 `WS_EX_*` 与 owner 的变化不产生任何 WinEvent。只靠事件会让已退出的窗口永久留在预览区。
- **影响**：PRD 5.3 的「避免轮询」改为「避免高频轮询」，1Hz 校准保留（PRD 5.7 允许每秒一次校验）；M1 的窗口模型必须包含同样的校准步骤。

## D-021 窗口分类要求顶层窗口且无 owner

- **日期**：2026-11-18
- **决策**：除不可见、DWM cloak、`WS_EX_TOOLWINDOW`、系统壳窗口外，窗口还必须是顶层窗口（`GetAncestor(hwnd, GA_ROOT) == hwnd`），且无 owner（有 owner 时只有带 `WS_EX_APPWINDOW` 才保留）。
- **理由**：记事本（Win11 版本）会创建大量名为 `Non Client Input Sink Window`、空标题的子窗口与附属窗口，并在创建时临时可见。缺少这两条规则时，一次 12 轮开关测试会在预览区模型里堆积 70+ 个幽灵窗口。
- **影响**：`airpane-core::window` 的 `WindowFacts` 增加 `top_level`、`owned`、`app_window`；新增 `RejectReason::NotTopLevel` 与 `RejectReason::OwnedPopup`。

## D-027 日志自写，不引入 tracing

- **日期**：2026-11-19
- **决策**：M1 的日志由 `airpane-platform-win::logging` 自实现：级别过滤、单文件 1MB、保留 `airpane.1.log` 到 `airpane.3.log` 三份历史、本地时间戳。不引入 `tracing` + `tracing-subscriber` + `tracing-appender`。
- **理由**：PRD 5.1 只是「建议」`tracing`。M1 需要的只有「把崩溃前最后几步留下来」，自写模块约 150 行、零新依赖、不改 CI 编译时间；`tracing` 的结构化字段与过滤能力在 M1 没有使用场景。M4 做日志导出时若确实需要结构化查询，再评估替换。
- **影响**：`docs/DEPENDENCIES.md` 不变；日志只写 hwnd、pid、进程名、错误码与状态迁移，不写窗口标题、窗口内容与用户输入（PRD 11.3 第 5 条）。

## D-029 状态文件按生命周期分三份

- **日期**：2026-11-19
- **决策**：`%APPDATA%\AirPane\` 下分四个文件：用户设置 `config.json`、崩溃恢复 `snapshot.json`、尺寸记忆 `window-sizes.json`、日志 `logs\airpane.log`。`APPDATA` 缺失时回退到可执行文件同级目录，保证便携运行也能留下文件。
- **理由**：三类数据生命周期不同——配置由用户手改，快照每次进入 Stage 都要重写，尺寸记忆由程序自动学习。混在一个文件里会让「每次移动窗口都重写用户配置」这种荒谬的写入模式出现，也让损坏时无法只重置其中一类。快照损坏时不该丢掉用户设置，反之亦然。
- **影响**：`airpane-platform-win::paths` 是唯一拼路径的地方；写快照不得触碰 `config.json`。

## D-024 退出还原与崩溃恢复的语义

- **日期**：2026-11-19
- **决策**：正常退出（快捷键退出、`WM_CLOSE`、进程结束前）先把所有被本程序移动过的窗口还原到快照位置，再把快照标记为 `clean_exit = true`；启动时读到 `clean_exit == false` 的快照，按快照恢复窗口位置后清除快照。只有快照里 `ShowState::Normal` 的窗口参与恢复：最大化与最小化窗口不会被 Stage 搬动（D-026），没有位置可还原。
- **理由**：AirPane 不在运行时，桌面上不应该存在形变过的窗口。同时，「未清理的快照」是崩溃与强杀的唯一信号，比在别处维护一个「上次是否正常退出」的独立标记更不容易失效。
- **影响**：`core::snapshot` 的 `SnapshotFile` 增加 `clean_exit`，版本升到 2；`platform-win::snapshot_store` 负责读写的原子性；`app::recovery` 是唯一的恢复入口。

## D-030 位置与尺寸统一使用 DWM 可见边界

- **日期**：2026-11-19
- **决策**：项目内所有窗口位置与尺寸计算（枚举结果、快照、舞台区居中、移动目标）统一使用 `DwmGetWindowAttribute(DWMWA_EXTENDED_FRAME_BOUNDS)`，拿不到时才回退 `GetWindowRect`。`SetWindowPos` 接受的是含阴影的外框，由 `platform-win::placement::move_window` 内部做一次补偿。
- **理由**：手工验证时发现，把 `GetWindowRect` 的结果当作「可见边界」再交给 `move_window` 补偿，会导致窗口每移动一次就膨胀一圈 —— 微信窗口从 1053×992 变成 1147×1079，因为 Qt 窗口的阴影外扩接近 50px。两处使用不同坐标系是这类 bug 的唯一来源，所以只允许一种语义。
- **影响**：`platform-win::window::extended_frame_bounds` 成为唯一的边界读取入口；`WindowInfo::rect` 与快照里的 `rect` 语义随之变为可见边界；`move_window` 的入参必须是同一语义的矩形。
## D-022 只移动当前活跃窗口，其余窗口原地不动

- **日期**：2026-11-19
- **决策**：Stage 模式下每次切换只对当前活跃窗口调一次 `SetWindowPos`，其余窗口保持原位。它们的缩略图在预览区里展示，点击即切换。
- **理由**：每轮切换只动一个窗口，闪烁与崩溃风险最小；被移动过的窗口集合最多等于用户实际用过的窗口数，快照与还原逻辑简单。代价是观感与 macOS 台前调度不同（其余真窗口不会堆到左侧），但预览区已经提供了同样信息的空间入口。
- **影响**：`app::App` 的 `moved` 集合；退出时按它逐个还原（D-024）。

## D-023 活跃窗口 = 前台窗口，实时跟随

- **日期**：2026-11-19
- **决策**：不区分「点缩略图切换」与「Alt+Tab / 任务栏 / 新开窗口」，只要可管理窗口成为前台就搬进舞台区。
- **理由**：唯一真相源是前台窗口，不需要额外的状态机，也不会出现「前台是 A、舞台区里是 B」的不一致。用户的反馈是 3 天自用后再判断要不要改成「仅点缩略图才移动」，M1 先按跟随实现。
- **影响**：`App::focus_window` 只由 `EVENT_SYSTEM_FOREGROUND` 驱动；M2 的暂停机制要在这一层前面加过滤。

## D-025 尺寸记忆按句柄优先、进程 + 类名回退，只记尺寸不记位置

- **日期**：2026-11-19
- **决策**：会话内按 hwnd 记录，跨运行按 `(process_name, class_name)` 合并；下次窗口进入舞台区时用记住的尺寸居中放置。占满舞台区的尺寸不记录。
- **理由**：同一应用的多个窗口在会话内必须分开，重启后能继承大致尺寸即可。位置每次由舞台区几何重算，预览区宽度或分辨率变化时窗口不会偏出舞台区。记录满屏尺寸没有记忆价值，只会让窗口永远满屏。
- **影响**：`core::window_sizes::WindowSizeStore`；`window-sizes.json`（D-029）。

## D-026 M1 的最小全屏/最大化保护（其中「最大化不搬」已由 D-037 取代）

- **日期**：2026-11-19
- **决策**：前台窗口处于最大化，或可见边界覆盖整个主显示器（允许 1px 误差）时，不移动、不缩放它，只在日志记一条；仍把它记为活跃窗口，避免预览区把它列成可切换项。
- **理由**：3 天自用必然遇到全屏视频与游戏。完整规则（进程名单、`SHQueryUserNotificationState`、暂停与 1 秒防抖）留给 M2，M1 只做「别去动它」这一条。
- **影响**：`platform-win::monitor::should_skip_placement`；`App::focus_window` 的跳过分支。

## D-031 系统 UI 宿主进程不进入预览区

- **日期**：2026-11-19
- **决策**：`StartMenuExperienceHost.exe`、`SearchHost.exe`、`ShellExperienceHost.exe`、`TextInputHost.exe`、`LockApp.exe` 的窗口一律排除，新增 `RejectReason::ShellProcess`。`WindowFacts` 增加 `process_name`。
- **理由**：手工验收时启动瞬间的前台窗口是开始菜单宿主，它通过了原有的可见性、顶层、类名规则，被当成普通窗口搬进了舞台区。这类窗口由系统 UI 进程创建，搬走会直接破坏开始菜单、搜索、音量面板与输入法候选框。类名规则拦不住它们（Win11 开始菜单用的是通用 XAML 宿主类名）。
- **影响**：`core::window::classify` 增加进程名判定；后续 M2 的用户自定义排除名单走同一条路径。

## D-032 预览区宽度从配置读取并应用 D-012 钳制

- **日期**：2026-11-19
- **决策**：`Strip::create` 接收配置里的 `strip.width_dip`，实际宽度 = `effective_strip_width` 的结果按窗口 DPI 换算成物理像素。
- **理由**：M0 把 200 DIP 写死在 `strip` 里，配置项形同虚设。现在宽度只有一条计算路径，舞台区宽度也直接用预览区的实际宽度，两者不会对不上。
- **影响**：`Strip::width()` 是舞台区计算的唯一输入；改宽度只需改配置文件。
## D-028 首次启动默认进入 Stage 模式

- **日期**：2026-11-19
- **决策**：配置项 `startup.mode` 的取值 `last`（默认）在 M1 等同于 `stage`；`normal` 会让程序以普通桌面模式启动。真正的「上次状态」需要单独记录运行态，留到 M3 设置面板。
- **理由**：M1 还没有设置面板与引导，默认形态是用户发现程序在工作的唯一方式。把「上次状态」塞进 `config.json` 会让程序每次切换模式都重写用户配置文件，违反 D-029 的生命周期划分。
- **影响**：`app::main` 的启动分支；M3 决定是否引入独立的运行态文件。

## D-033 工具区文字 M1 硬编码，M3 换资源表

- **日期**：2026-11-19
- **决策**：预览区底部工具区的两个按钮文字（「设置」「桌面」）在 M1 以常量数组写死在 `airpane-strip`，集中在一个 `TOOLBAR_LABELS` 里。
- **理由**：PRD 11.3 第 8 条要求用户可见文字走多语言资源，但 M1 没有任何资源系统，为一个 40 像素高的工具栏引入 i18n 框架不划算。集中成常量是为了 M3 引入资源表时只需要改一处。
- **影响**：`crates/strip/src/window.rs` 的 `TOOLBAR_LABELS`；M3 设置面板落地时必须一起处理这条硬约束。

## D-034 最小化窗口：先同步还原再搬入，尺寸只记普通状态

- **日期**：2026-11-19
- **决策**：前台窗口处于最小化时，`App::focus_window` 先调用 `foreground::restore`（同步 `ShowWindow(SW_RESTORE)`），重新读取矩形后再走正常搬入流程。尺寸记忆只记录 `ShowState::Normal` 的窗口，且尺寸不小于舞台区时不记。
- **理由**：`SetWindowPos` 对最小化窗口只修改「还原位置」，窗口仍留在 `-32000` 一行，表现为「日志说已移入舞台区，窗口却还在任务栏」。而 `activate` 里的 `ShowWindowAsync` 是异步的，紧接着读到的矩形可能还是最小化时的 `146x21`，这个尺寸一旦写进尺寸记忆，下次进入舞台区就会按它居中，窗口变成一条细缝。
- **影响**：`platform-win::foreground::restore` 是唯一同步还原入口；`App::remember_size` 增加状态与尺寸下限两个前置条件。
## D-035 校准策略：已跟踪窗口 + 每 10 秒全量兜底

- **日期**：2026-11-19
- **决策**：1Hz 校准只对注册表里已有的窗口做 `inspect_window` 复核；每 10 次（即 10 秒）做一次全量 `EnumWindows` 兜底。预览区列表没有实际变化时不调用 `DwmUpdateThumbnailProperties`。新窗口依赖 `EVENT_OBJECT_CREATE` / `SHOW` 事件发现。
- **理由**：M1 验收第一次测得 20 个窗口时空闲 CPU 2.11%，超过 1% 的门槛。实测开销集中在每秒一次的全量枚举（本机 290 个顶层窗口 × 每个 10 次 Win32 查询）与每秒无条件重建 19 个缩略图属性。改为上述策略后同一场景降到 0.39%。
- **影响**：`App::reconcile` 与 `App::sync_strip`；D-020 的「1Hz 校准」细化为「已跟踪校准 1Hz + 全量兜底 10 秒」。若以后发现新窗口漏检，再缩短全量间隔或监听更多事件。

## D-036 桌面成为前台时隐藏预览区

- **日期**：2026-11-19
- **决策**：前台窗口的类名是 `Progman` 或 `WorkerW`（Win+D、点「显示桌面」、关闭全部窗口后）时，隐藏预览区；下一个可管理窗口成为前台时恢复显示。配置里的预览区位置仍默认左侧。
- **理由**：用户反馈按 Win+D 看桌面时，预览区遮住左上角的桌面图标。预览区是 `WS_EX_TOPMOST` 的工具窗口，不会被 Win+D 最小化。换到右侧只是把遮挡挪个角落；看桌面时本来就不需要预览区。
- **影响**：`platform-win::window::is_desktop_window`；`App` 新增 `desktop_hidden` 状态，`leave_stage` 时重置。

## D-037 最大化窗口在 Stage 模式下摆到舞台区

- **日期**：2026-11-19
- **决策**：Stage 模式下，处于最大化状态的前台窗口先 `SW_RESTORE` 取消最大化，再摆进舞台区；快照记录 `ShowState::Maximized`，切回普通桌面时用 `SW_MAXIMIZE` 恢复原来的最大化状态。非最大化但覆盖整屏的窗口（游戏、全屏视频）仍然不搬动。
- **理由**：原来的 D-026 让最大化窗口停在整屏，直接盖住预览区，台前调度当场失效。用户明确要求「最大化 = 舞台区」。
- **影响**：`monitor::should_skip_placement` 改为 `is_exclusive_fullscreen`（只判真全屏）；`App::focus_window` 处理最大化；新增 `App::enforce_active_bounds`，因为「在舞台区窗口上点最大化」不会产生前台事件，只能靠 1Hz 校准发现。
- **已知风险**：取消最大化会让窗口短暂经历一次尺寸过渡；少数应用可能自己抢回最大化，遇到就记进测试报告。

## D-038 光标由窗口类显式指定

- **日期**：2026-11-19
- **决策**：`AirPaneStrip` 的 `WNDCLASSW` 设置 `hCursor = LoadCursorW(None, IDC_ARROW)`。
- **理由**：用户反馈鼠标移入预览区变成转圈（等待）光标。不设类光标时 `DefWindowProc` 不会主动设置，鼠标形状会继承上一个窗口留下的状态；而 `activate` 会启动/还原应用，系统在其他窗口上留下的等待光标就被带进了预览区。
- **影响**：`crates/strip/src/window.rs` 的窗口类注册；实测预览区与桌面的光标句柄一致。


## D-039 最大化不写入尺寸记忆，并清理旧记录

- **日期**：2026-11-19
- **决策**：原本处于最大化状态的窗口被搬进舞台区时强制占满舞台区（忽略尺寸记忆），并删除该窗口已有的尺寸记忆；`focus_window` 在“同一窗口重新获得焦点”分支里，只有窗口处于普通状态才记录尺寸。
- **理由**：用户反馈 Edge 与 `winc.exe` 点最大化后“闪回小窗口”。实测尺寸记忆里存着 `msedge.exe: 1280x1440`、`winc.exe: 1692x1047`——它们是 `SW_RESTORE` 之后读取到的**最大化还原尺寸**，被当成用户的尺寸偏好记录了下来，之后每次进舞台区都按它居中，并随着每次记录自我强化。资源管理器与微信没有这类记录，所以表现正常。
- **影响**：`App::target_rect` 增加 `force_stage` 参数；`WindowSizeStore` 新增 `remove`；`App::flush_sizes` 统一写盘。用户手动调整舞台区窗口尺寸的行为不变（实测 1200×800 会被记住并在下次居中）。

## D-040 新搬入窗口有 3 秒观察期

- **日期**：2026-11-19
- **决策**：窗口被搬进舞台区后进入 3 秒观察期（`SETTLE_WINDOW`）。观察期内 1Hz 校准会检查它的矩形是否偏离目标，偏离就重新摆放一次；观察期内不写入尺寸记忆。之后不再干预，用户手动调整尺寸照旧生效。
- **理由**：用户反馈「任何程序启动都是小窗口，切走再切回才铺满」。新程序启动时，应用自己的初始化代码常在我们的 `SetWindowPos` 之后把窗口改回默认尺寸。观察期既能把这类覆盖纠正回来，又不会永久劫持用户的尺寸调整。
- **影响**：`App::settle_until`、`App::enforce_settle`；`reconcile` 在观察期内跳过 `remember_active_size`，避免把应用初始化的尺寸写进记忆。

## D-041 全屏判定加入窗口样式启发式

- **日期**：2026-11-19
- **决策**：`is_exclusive_fullscreen` 除了「覆盖整屏且未最大化」，再要求窗口**没有** `WS_CAPTION` 与 `WS_MINIMIZEBOX` 才算真全屏。
- **理由**：任务计划程序（`mmc.exe`）用 `WS_POPUP` 自定义最大化，`IsZoomed` 返回 false 但窗口覆盖整屏。原判定把它当成全屏游戏跳过，于是它一直铺满屏幕盖住预览区。带上标题栏或最小化按钮的窗口说明是应用自己放大，不是全屏展示。
- **影响**：`platform-win::window::has_window_style`；M2 会用 `SHQueryUserNotificationState` 与进程名单替换这条启发式。
- **已知限制**：浏览器 F11 全屏可能保留 `WS_MINIMIZEBOX`，会被误当作最大化搬走。M2 修正。

## D-042 release 不申请控制台，并做最小单实例检测

- **日期**：2026-11-19
- **决策**：`airpane` 在非 debug 构建下使用 `#![windows_subsystem = "windows"]`，不创建控制台窗口；debug 构建保留控制台方便调试。启动时按预览区窗口类名检测已有实例，命中就弹一次提示并退出。
- **理由**：用户以管理员身份启动 release 版时报「弹个终端出来」，那是 console 子系统的控制台窗口。常驻后台程序不该有它，提权启动时尤其明显。同时提权与普通权限各跑一个实例会互相抢窗口和 `Ctrl+Alt+S`，第二个实例注册快捷键会失败并弹框，体验很差。
- **影响**：`crates/app/src/main.rs` 的 crate 属性与启动检查；`platform-win::window::find_window_by_class`。完整的单实例（唤起已有实例并打开设置面板）仍然留给 M3。
- **已知限制**：release 版没有控制台，启动信息只能看 `%APPDATA%\AirPane\logs\airpane.log`。

## D-043 预览区不做半透明，M3 用 DirectComposition 重写渲染

- **日期**：2026-11-19
- **决策**：M1 的预览区保持不透明纯色背景。不做整窗半透明，也不做 Acrylic 背景。「缩略图清晰 + 背景通透」的 macOS 台前调度观感，改为 M3 用 DirectComposition 自绘渲染实现。
- **理由**：两次实验都走了到底。`WS_EX_LAYERED` 加 alpha 能让窗口半透明且缩略图正常显示，但 alpha 是整窗生效，缩略图 `opacity` 上限是 255，无法比背景更实，结果是缩略图一起变淡。`WS_THICKFRAME` + `DwmExtendFrameIntoClientArea(-1)` + `DWMWA_SYSTEMBACKDROP_TYPE = DWMSBT_TRANSIENTWINDOW` 三个 API 全部返回成功，但窗口仍是纯黑不透明（系统透明效果已开启）。色键透明会把缩略图里的同色像素一并扣掉。macOS 那边用的是自绘合成层，这在 Windows 上对应 DirectComposition。
- **影响**：`crates/strip/src/window.rs` 保持 GDI 纯色绘制；M3 的渲染重写任务包含这项。实验过程与结论同时记在 AGENTS.md 的「已经踩过的坑」，避免以后重复尝试。

## D-044 预览区标题取「分隔符分段」的中间段

- **日期**：2026-11-19
- **决策**：预览区标题只认 `" - "` 作为分隔符：分段（去掉空段）≥ 3 时取倒数第二段，否则取第一段；结果为空时显示进程名。规则实现为 `core::title::short_title`，纯逻辑带单测；预览区在同步时算一次，标题变化靠已有的 `EVENT_OBJECT_NAMECHANGE` 触发刷新。
- **理由**：200 DIP 宽的预览区放不下完整标题。Windows 应用的标题几乎都是「文档 - 项目或文件夹 - 应用名」，倒数第二段正好是用户认得的那一层：VS Code 显示项目名、资源管理器显示文件夹名。放在 `core` 里是为了能脱离 Win32 单测各种标题形态。
- **影响**：新增 `crates/core/src/title.rs`；`StripItem` 增加 `pid`、`class_name`、`process_name`、`title` 字段，`app` 与 `preview_strip` 示例同步填充。
- **已知限制**：Edge 的「页面标题 - 个人 - Microsoft Edge」会显示成「个人」。标题规则不做按应用的特例，等真实使用反馈再决定要不要加。

## D-045 预览区信息条、内边距与悬停放大参数

- **日期**：2026-11-19
- **决策**：每项改成「缩略图 + 底部 20 DIP 信息条」，信息条内左侧 16 DIP 应用图标、6 DIP 间距、右侧标题（超长用省略号截断），没有图标的项也保留图标位置以保证标题左边缘对齐。列表内边距 8 DIP、项间距 6 DIP。悬停项的缩略图区按 6/5 放大（+20%），上限仍是 160 DIP，下方项顺移，不做过渡动画。悬停用 `TrackMouseEvent(TME_LEAVE)` 收 `WM_MOUSELEAVE` 复位，悬停状态按窗口句柄记录而不是下标，列表重排后依然对得上。
- **理由**：只有缩略图的预览区认不出是哪个窗口，标题是刚需。悬停放大是为了在不加宽预览区的前提下看清某一项。无动画遵循 D-018（过渡动画属于 M3）。
- **影响**：`layout_entries` 增加 `hovered` 参数，`Entry` 增加 `bar`、`title`、`icon` 字段；`WM_MOUSEMOVE` 与 `WM_MOUSELEAVE` 分支；命中测试把信息条也算进项内，点信息条同样切换窗口。
- **已知限制**：已经顶到 160 DIP 的高窗口悬停不再放大；放大只用重排实现，鼠标停在两项交界处时高度会跳变一次。

## D-046 应用图标三级兜底，按 (pid, 类名) 缓存

- **日期**：2026-11-19
- **决策**：图标按 `WM_GETICON`（`ICON_BIG` → `ICON_SMALL2` → `ICON_SMALL`）→ `GetClassLongPtrW(GCLP_HICON)` → `SHGetFileInfoW(SHGFI_ICON | SHGFI_SMALLICON)` 取 exe 图标 的顺序三级兜底。缓存键是 `(pid, 类名)`，随预览区列表同步清理。前两级拿到的句柄不属于本进程，不能 `DestroyIcon`；第三级由 `SHGetFileInfoW` 分配，交给 `AppIcon` 的 Drop 释放。
- **理由**：只靠 `WM_GETICON` 会漏掉一批不设窗口图标的程序（终端、部分 Qt/Electron 应用），而只看 exe 图标又会把「同一进程不同类用不同图标」的场景抹平。缓存按类名区分、按 pid 分组，兼顾两者；`AppIcon` 记住所有权是因为销毁别人的图标句柄会破坏系统图标缓存。
- **影响**：新增 `platform-win::icon`；`platform-win::window` 抽出 `process_path`（原 `query_process_name` 内部逻辑）。`Cargo.toml` 的 `windows` feature 增加 `Win32_UI_Shell` 与 `Win32_Storage_FileSystem`——`SHGetFileInfoW` 同时被这两个 feature 门控，只开前者编不过。
- **已知限制**：`WM_GETICON` 用 `SendMessageTimeoutW` + `SMTO_ABORTIFHUNG`（每次查询 100ms 超时）发送，无响应的应用最多少见地拖慢一次同步；图标加载发生在同步路径上，不做后台线程（一次会话里每个应用只付一次）。`SHGFI_SMALLICON` 取的是系统小图标，高 DPI 下靠 `DrawIconEx` 放大，150% 以上会略糊（DPI 验收缺口，M4 补齐）。

## D-047 预览区改用固定顺序，不再按最近使用排序

- **日期**：2026-11-19
- **决策**：预览区列表按 `(进程名, 类名, 句柄)` 升序固定排列，前两项忽略大小写，活跃窗口不显示。排序逻辑放在 `core::registry::display_key`（纯函数带单测），`app::sync_strip` 排序后再同步。刻意不比较标题。
- **理由**：MRU 让刚失去焦点的窗口插到最上面，连着点两个应用时第 1、2 项反复互换，用户报「排序乱跳」。查日志确认这是设计行为而非 bug（每次点击只移动一个窗口）。固定顺序让同一个窗口永远待在同一位置，点开一个只让它消失；不比较标题是因为浏览器换标签页、编辑器换文件都会改标题，按标题排会把「乱跳」带回来。
- **影响**：新增 `core::registry::display_key`；`app::sync_strip` 改为先排序再建列表；`preview_strip` 示例同步排序。注册表内部仍保留 MRU（`WindowRegistry`），仅供校准与调试使用。
- **已知限制**：同一应用同类名的多个窗口按句柄（创建顺序）排，旧窗口销毁后新窗口会排到同类末尾。

## D-048 预览区不显示标题，改成 40 DIP 的大图标条

- **日期**：2026-11-19
- **决策**：每项布局从「缩略图 + 20 DIP 信息条（16 DIP 图标 + 标题）」改成「缩略图 + 40 DIP 图标条（32 DIP 应用图标，左对齐缩略图左边缘）」。不显示标题，`core::title::short_title` 与 `StripItem` 的 `title` / `process_name` 字段随之删除。exe 图标兜底从 `SHGFI_SMALLICON` 换成 `SHGFI_LARGEICON`。
- **理由**：用户对照 macOS 台前调度截图反馈「图标太小、标题太小」。macOS 左栅没有标题，只有大图标；32 DIP 正好是 `ICON_BIG` 与大文件图标的原始尺寸，不需要缩放。
- **影响**：D-044（标题规则）不再有展示位，`crates/core/src/title.rs` 删除；D-045 的 20 DIP 信息条参数作废，换成 `ICON_BAND_DIP = 40`、`ICON_DIP = 32`、`ICON_INSET_DIP = 8`；`paint` 只画图标。
- **已知限制**：DWM 缩略图由系统合成在窗口内容之上，图标不能像 macOS 那样压在缩略图角上，只能放在缩略图下方的条里；圆角与阴影同理由 M3 的 DirectComposition 解决。只有图标时，两个同类窗口（例如两个终端）无法从图标区分。

## D-049 悬停改成高亮，取消放大与顺移

- **日期**：2026-11-19
- **决策**：悬停项的图标条背景从 `0x2B2B2B` 提到 `0x383838`，并在图标条上沿画 3 DIP 的浅蓝强调条（`RGB(80,160,255)`）。取消 D-045 的「悬停缩略图 +20% 放大、下方项顺移」，布局不再依赖悬停状态；悬停变化只重绘，不重排。
- **理由**：鼠标经过时整列上下滑动是「排序乱跳」感受的一部分，而放大本身对识别窗口没有帮助。高亮不改变任何几何，列表完全静止。
- **影响**：`layout_entries` 去掉 `hovered` 参数与 `HOVER_NUM / HOVER_DEN`；`wnd_proc` 的 `WM_MOUSEMOVE` / `WM_MOUSELEAVE` 只调 `InvalidateRect`；`paint` 增加悬停配色。
- **已知限制**：DWM 缩略图覆盖了项的大部分面积，高亮只能画在图标条上，视觉强度比不上 macOS 的整项高亮。

## D-050 应用图标：多尺寸 ico + 自写 build.rs 调 rc.exe

- **日期**：2026-11-19
- **决策**：把用户设计的 `airpane.png` 转成 `assets/airpane.ico`（16/24/32/48/64/128 用 32 位 DIB，256 用 PNG 帧），连同 `assets/airpane.rc` 由 `crates/app/build.rs` 调 Windows SDK 自带的 `rc.exe` 编成 `.res` 再交给链接器（`cargo:rustc-link-arg`）。预览区窗口类的 `hIcon` 用同一个资源 id。小尺寸直接由原图缩放，不做简化版（用户确认）。
- **理由**：不用 `embed-resource` / `winres`——它们会带进 20 多个构建期依赖（toml、winnow、cc、vswhom…），而这件事只需要一次 `rc.exe` 调用。`rc.exe` 随 Windows SDK 安装，MSVC 工具链的开发机与 CI 都会有。
- **影响**：新增 `assets/{airpane.ico,airpane.rc}`、`crates/app/build.rs`；`windows` crate 无需新 feature（`LoadIconW` 已在 `Win32_UI_WindowsAndMessaging`）；`Cargo.lock` 没有变化。示例程序（如 `preview_strip`）没有这份资源，加载失败就退化为无窗口图标。
- **已知限制**：图标整体偏白且大量半透明，缩到 16/24 px 后只剩一团淡色轮廓，任务栏与资源管理器里待建议另外出一张简化图；另外 `rc.exe` 路径按 `%ProgramFiles(x86)%\Windows Kits\10\bin\*\x64` 取最高版本，自定义安装位置会找不到（会直接报错，不会静默生成无图标的 exe）。

## D-051 预览区也显示当前窗口，并用快照矩形稳住项高

- **日期**：2026-11-19
- **决策**：预览区列出**全部**被管理窗口（D-047 的「活跃窗口不显示」作废），当前在舞台区的窗口用浅蓝强调条 + 更亮的图标条标出；点它不做事。活跃项的宽高比用快照里的原始矩形（`moved`）而不是搬入后的舞台区矩形。
- **理由**：用户明确「不能接受侧边栏切换时变来变去」。把当前窗口也留在列表里，切换时列表内容完全不变，只有高亮换位置 —— 这是唯一能完全消除位移的做法。用快照矩形是因为活跃窗口的矩形变成 `2360×1440` 后宽高比会变（D-030 的可见边界），项高跟着变就会把下方全顶动，换一种方式继续跳。
- **影响**：`StripItem` 新增 `active` 字段；`app::sync_strip` 不再过滤活跃窗口，并按 `self.moved` 取活跃项矩形；`Entry.active`；`paint` 增加活跃配色（图标条 `0x3C3C3C` + 3 DIP 强调条）；`hit_test` 改为返回 `&Entry`，点击活跃项直接忽略。
- **已知限制**：活跃窗口是活缩略图，但它被拉伸到按原矩形算出的目标矩形，宽高比不一致时会轻微变形；如果用户手动拖动活跃窗口改变尺寸，项高仍会变（非切换引起）。

## D-052 当前窗口盖住整屏时隐藏预览区

- **日期**：2026-11-19
- **决策**：当前活跃窗口的可视边界覆盖整个显示器时隐藏预览区，回到不覆盖的窗口再显示。判定用 `monitor::covers_primary_monitor`，比 D-041 的 `is_exclusive_fullscreen` 宽；在前台事件、`enter_stage` 与 1Hz 校准里各检查一次。
- **理由**：用户反馈浏览器全屏播放视频时预览区没有隐藏，反而浮在视频上方（预览区是 `WS_EX_TOPMOST`）。用「覆盖整屏」而不是「无标题栏 + 无最小化按钮」：浏览器 F11 会保留标题栏样式，严格规则会漏掉；而只要窗口真的盖住整屏，置顶的预览区就一定会遮挡。1Hz 校准是必需的：在同一个窗口里点全屏不产生前台事件。
- **影响**：`App::fullscreen_hidden` 与 `App::sync_fullscreen_visibility`；`on_event(Foreground)`、`enter_stage`、`reconcile` 各调一次；`leave_stage` 重置两个隐藏标志。
- **实测**：无边框全屏窗口在前台时 `IsWindowVisible(AirPaneStrip)=false`，关闭后恢复 `true`；另一个用例是窗口先被搬进舞台区、随后自己长到全屏（无前台事件），1Hz 校准也能在 1 秒内隐藏。
- **已知限制**：任务栏设为自动隐藏时，普通最大化窗口也会覆盖整屏从而隐藏预览区。语义上一致（窗口确实盖住了屏幕），但如果你常用自动隐藏任务栏则需要放宽这条。

## D-053 预览区支持拖动排序，顺序落盘

- **日期**：2026-11-19
- **决策**：按住缩略图上下拖动改变顺序，松手落位；阈值 4 DIP，超过才算拖拽，否则松开仍是点击切换。顺序按「进程名 + 类名」（两份都转小写）记录在 `%APPDATA%\AirPane\strip-order.json`，跨重启生效。没记录过的窗口排在已记录项之后，组内仍按 D-047 的固定顺序；新窗口自然排到末尾（用户确认）。
- **理由**：D-047 的固定字母序能防「乱跳」，但无法表达「这两个应用我想放在一起」。手动排序叠加在固定序之上：拖过的项位次由人决定，没拖过的仍可预测。排序单位用（进程名、类名）而不是句柄：句柄跨重启会变，标题又经常变。
- **影响**：新增 `core::strip_order`（纯逻辑 + 7 个单测）、`platform-win::strip_order_store`、`paths::strip_order_file`；`App::new` 改收 `AppPaths`；`App::reorder` / `flush_order`；`StripAction::Reorder`；`strip` 的 `Drag` 状态、`layout::drop_index` / `drop_line`、`WM_LBUTTONUP` / `WM_CAPTURECHANGED` 处理与 2px 强调色指示线。
- **实测**：真实桌面拖动第二项到顶部 → `strip-order.json` 写入该键；重启后拖第二项→顶部，结果证明上次的顺序被正确加载；拖到自己身上不写盘、不改顺序。
- **已知限制**：同一应用的同类窗口作为一组一起移动（无法单独排两个终端）；排序文件只增不减（已退出的应用、关闭多年的窗口仍在表里），文件很小但有洁癖可手动删；同一位置拖到下一个边界会被当作「原位」而不是重排（避免无意义的写盘）。

## D-054 预览区跟随系统浅色/深色主题

- **日期**：2026-11-19
- **决策**：预览区配色改成两套（`paint::DARK` / `paint::LIGHT`），启动时读 `HKCU\Software\Microsoft\Windows\CurrentVersion\Themes\Personalize\AppsUseLightTheme` 选一套；`WM_SETTINGCHANGE` 时重读并重绘，不同步就不动。读不到注册表时回退深色。
- **理由**：用户反馈浅色主题下左侧一整块黑边很突兀（本机当前就是浅色模式）。跟随系统是 Windows 应用的默认期待，比新增一个配置项更少维护成本。
- **影响**：新增 `platform-win::theme`（`SHGetValueW` 读注册表，`windows` feature 加 `Win32_System_Registry`）；`paint` 从常量改成 `Palette`，`StripState.scheme`。
- **已知限制**：只认「应用模式」，不跟随自定义强调色；主题切换时只重绘本窗口，已画的缩略图由 DWM 实时重新合成，不需要额外处理。

## D-055 隐藏预览区后催一层重绘（当时未复现，仅作缓解）

- **日期**：2026-11-19
- **决策**：隐藏预览区后对前台窗口发一次 `RedrawWindow(RDW_INVALIDATE | RDW_ALLCHILDREN)` 再 `DwmFlush()`，让被盖住的区域立刻重画。故意不用 `RDW_UPDATENOW` —— 那会同步给别的进程发 `WM_PAINT`，对方卡死时本线程跟着卡。
- **理由**：用户反馈全屏视频隐藏预览区的一瞬能看到部分桌面。
- **实测情况**：用一个黑色无边框全屏窗口 + 30ms 间隔截图采样（277 帧），开关这段代码各跑一遍，两遍都没采到桌面像素 —— 说明脚本化场景复现不了真实播放器的这一帧。因此这条是低风险缓解，**未证实有效**，需要在真实播放器下复验。
- **影响**：新增 `platform-win::compose::redraw_now`；`App::update_strip_visibility` 在隐藏分支调用一次。

## D-057 用 LOCATIONCHANGE 事件把全屏显隐延迟从 ~1 秒降到几十毫秒

- **日期**：2026-11-19
- **决策**：监听 `EVENT_OBJECT_LOCATIONCHANGE`，但**只把前台窗口的矩形变化投递成 `WindowEvent::BoundsChanged`**；`App::on_event` 收到后只调一次 `update_strip_visibility`，不枚举、不搬窗口。同时把前台事件里的可见性判断提到 `refresh_registry` / `focus_window` **之前**，判定参数从 `self.active` 改为传进来的前台句柄；显示前先 `InvalidateRect` + `UpdateWindow`，避免第一帧是空白。
- **理由**：D-055 只解决了「进入全屏时下层窗口不重画」，而用户实测退出全屏仍露桌面。根因是在同一个窗口里点全屏/退全屏**不产生前台事件**，只能等 1Hz 校准；再加上前台事件里要先枚举近 300 个窗口再搬窗口，这段耗时里桌面就露出来了。
- **实测（真实 Chrome 视频页 + 模拟按键，两种代码各跑一遍）**：

| 方向 | 修复前 | 修复后 |
| --- | --- | --- |
| 按 F 进全屏，预览区隐藏 | 368 ms | 42 ms |
| 按 Esc 退全屏，预览区恢复 | 982 ms | 26 ms |

- **影响**：`events::WindowEvent::BoundsChanged`、`events::is_foreground`；LOCATIONCHANGE hook 区间；`App::update_strip_visibility(strip, foreground)`；`Strip::set_visible` 先画后显。
- **已知限制**：只转发前台窗口的事件，后台窗口拖拽不会触发可见性判断；拖拖前台窗口时如果它恰好盖满屏幕，预览区会隐藏（语义上正确）；若某应用进出全屏根本不改窗口矩形，仍靠 1Hz 兑底，最多晚一秒。

## D-056 输入法使用期间某些窗口的缩略图会变黑（DWM 限制）

- **日期**：2026-11-19
- **决策**：不处理。`winc.exe` 在用输入法时预览区里的缩略图会整块变黑，输入结束后自行恢复；这是 DWM 在窗口表面切换（输入法候选窗口、硬件表面）期间的采样限制，M1 不做像素检测、不做降级占位。
- **理由**：要检测“缩略图是不是黑的”只能自己截图采像素，既违背 PRD 11.3 第 5 条的精神（窗口画面只用于 DWM 缩略图实时显示），又会把开销从合成层搬到 CPU。而 M3 的 DirectComposition 自绘渲染会重新处理这一块。
- **影响**：无代码改动；记入 AGENTS.md 的踩坑清单与 M1 测试报告的已知缺口。
